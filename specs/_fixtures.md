specs means an example row transcribes straight into `tests/fixtures/` without a
translation step, and two rules describing the same item are visibly about the
same item.

Do not invent a new incident key for a new example. Add to this file instead.

from a real Jira Server 8.20.10 (`issues.apache.org/jira`), and the content is

| `status` / `issuetype` / `priority` / `resolution` | `Done` / `Incident` / `High` / none |
| `description` | wiki markup: an `h2. Impact` section stating the loss, `CHF 48'200`, and no root cause |

**Per-field gold answers are not recorded for the corpus as a whole.** Writing
expected values nobody verified is inventing a threshold by another name. What is

built to say. The one exception is `INC-5455` in the scoring example below, whose
`root_cause` of `null` is exactly its recorded defect.

## Gold set

A workspace asset, resolved where `dossier` runs rather than against a pipeline's
own directory, so one set can serve several pipelines (R3.7).

| Path | Holds |
|---|---|
| `gold/incidents/` | the verified answers, one `<document>.json` per document |
| `gold/incidents/samples/root_cause.jsonl` | the human-scored cases a judge is measured against: candidate answers marked supported or unsupported, wrong ones included (R7.16) |
| `gold/incidents/judge.yaml` | the agreement each judged field's judge must reach — `root_cause: 0.95`, agreed by `a.aleks` (R7.13) |
| `gold/incidents/calibrations/root_cause.json` | what `dossier calibrate` measured for that judge: its model, the rubric hash, the judge prompt hash, the agreement and the sample size (R7.14, R7.19) |
| `.dossier/cache/judge/` | the judge's verdicts, one artifact per (judge, rubric, prompt, document, candidate), with a provenance record each (R7.18) |
| `gold/empty/` | a gold directory holding no `<document>.json`: nothing has been verified yet. What R12.1 refuses to publish as a dataset of nothing |

Three artifacts, and only the last is written by a machine. The sample and the
bar are both a person's: what a judge is *shown* and what it is *required* to
score are agreed, and what it *scored* is measured. A calibration run able to
rewrite either would not be gated by them.

## Converters

An id and a version, in the pair `(media type, kind)` each one claims. The
versions are deliberately unequal and deliberately not `1.0.0`: R5.4 is about
what happens when one of them moves, and a table of identical versions hides an
example that reads the wrong field.

| Converter | Claims | Version |
|---|---|---|
| `pdf-markdown` | `(application/pdf, markdown)` | `1.3.0` |
| `pdf-images` | `(application/pdf, page_images)` | `0.9.1` |
| `markdown-text` | `(text/markdown, markdown)` | `1.0.0` |

`1.4.0` is `pdf-markdown` after an improvement — the raised version every R5.4
example refers to.

The versions above are the **spec's** vocabulary: `1.3.0` and `1.4.0` exist so
that R5.4's examples have two versions to move between. The converters that
actually ship start at `1.0.0` and move on their own schedule, and a reader
comparing an example row against an installed package should expect them to
differ.

| Shipped converter | Claims | Extra |
|---|---|---|
| `markdown-text` | `(text/markdown, markdown)` | core |
| `text-plain` | `(text/plain, markdown)` | core |
| `pdf-markdown` | `(application/pdf, markdown)` | `dossier[pdf]` |
| `pdf-images` | `(application/pdf, page_images)` | `dossier[pdf]` |

## Scoring example (R7.2)

Four documents, the five fields `incident.yaml` declares. The gold table is what
a person writes into `gold/incidents/<document>.json`, in spec 007's format; the
tests do not write it. `affected_systems` is one reference string, because a
field record's value is a scalar (spec 006). `root_cause` is `null` throughout,
so it is scored on abstention (R7.3) and every verdict is deterministic.

| Document | `loss_amount` | `resolution_date` | `severity` | `affected_systems` | `root_cause` |
|---|---|---|---|---|---|
| `INC-4821` | `48200.00` CHF | `2026-07-28` | `major` | `payments-api, ledger-batch` | `null` |
| `INC-4822` | `12500.00` CHF | `2026-08-04` | `minor` | `ledger-batch` | `null` |
| `INC-4901` | `0.00` CHF | `2026-08-11` | `critical` | `payments-api` | `null` |
| `INC-5455` | `3100.00` CHF | `2026-08-19` | `major` | `upload-service` | `null` |

The run agrees with gold everywhere except here:

| Document | Field | Run answers | Verdict |
|---|---|---|---|
| `INC-4901` | `resolution_date` | `2026-08-12` | incorrect; does not match |
| `INC-5455` | `affected_systems` | `payments-api` | incorrect; does not match |
| `INC-4822` | `root_cause` | `disk pressure on the batch host` | incorrect; gold abstains (R7.3) |
| `INC-5455` | `root_cause` | `an unbounded retry loop` | incorrect; gold abstains -- the run picked one of the competing hypotheses |

Per field: `loss_amount` 100.0%, `resolution_date` 75.0%, `severity` 100.0%,
`affected_systems` 75.0%, `root_cause` 50.0% -- the weakest. Overall 80.0%, 16
of 20. Every figure is exact, so no rounding rule is needed to state it.

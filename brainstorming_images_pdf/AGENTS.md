# AGENTS.md — Evidence-Centric Document Audit Challenge

## Mission

You are acting as an **architecture challenger** for an existing document-analysis project.

The existing project was initially designed around analysing PDF documents, extracting their content, summarising them, and answering questions over a collection of documents.

The goal of this challenge is to determine whether the architecture should evolve into a more general:

> **Evidence-Centric Document Audit Engine**

The system should eventually be capable of auditing different types of documents and evidence sources, not only PDFs.

Examples:

- Postmortems
- Internal procedures
- Change-management documentation
- Jira incidents
- Jira change tickets
- Confluence pages
- Other structured or unstructured evidence sources

Do not assume the existing architecture is correct.

Your responsibility is to inspect the current implementation and critically determine what should be changed, added, removed, or redesigned.

---

# Core Architectural Principle

Do NOT model the system as:

```text
PDF → chunks → embeddings → RAG
```

Instead, investigate an architecture closer to:

```text
Sources
   ↓
Source-specific extraction
   ↓
Normalized evidence representation
   ↓
Claims + Evidence + Provenance
   ↓
Audit criteria
   ↓
Audit assessment
   ↓
Findings
```

The PDF, Jira ticket, Confluence page, screenshot, etc. are **sources**.

They are not the canonical representation of the information.

The system should create a reusable, provenance-preserving representation of the evidence contained in those sources.

---

# Primary Challenge

Determine whether the current project can support the following scenario.

## Scenario

There are approximately:

- 20 postmortem PDFs
- 20 internal procedure/process documents
- Jira incidents
- Jira change tickets
- potentially other evidence sources

An external auditor provides a set of questions or audit requirements.

Examples:

> Is there evidence that incidents are investigated to identify root cause?

> Is there evidence that corrective actions are defined?

> Is there evidence that corrective actions were actually implemented?

> Is there evidence that changes are properly approved?

> Is there sufficient evidence supporting the stated root cause?

The system should identify relevant evidence and provide a traceable answer.

The answer must not simply be generated from semantic similarity.

It must be possible to trace:

```text
Audit Criterion
      ↓
Assessment
      ↓
Claim
      ↓
Evidence
      ↓
Original Source
      ↓
Exact Location
```

# Challenge the Existing Architecture

## 1. Current document model

Determine:

- How PDFs are represented
- How pages are represented
- How sections are represented
- How tables are represented
- How images are represented
- How extracted text is stored
- How metadata is stored
- Whether page/section provenance is retained

Identify anything that would make future evidence traceability difficult.

## 2. PDF-specific assumptions

Look for assumptions such as:

```text
PDF
page
chunk
PDF parser
PDF embedding
PDF document
```

Determine which concepts should remain PDF-specific and which should become generic.

The architecture should ideally allow:

```text
PDF
Jira
Confluence
Email
Ticket
Screenshot
Monitoring export
```

to feed the same downstream audit engine.

## 3. Canonical evidence model

Design a model that can represent evidence independently of its original source.

At minimum investigate concepts such as:

```text
Source
Document
Section
Claim
Evidence
Event
Reference
AuditCriterion
AuditFinding
```

Do not blindly adopt these entities. Determine whether they are appropriate.

For every proposed entity explain:

- Why it exists
- What information it stores
- Its relationship to other entities
- Whether it is persisted
- Whether it is generated by an LLM or deterministic extraction
- How provenance is retained

## 4. Separate claims from evidence

This distinction is mandatory to investigate.

Example:

```text
Claim:
"The Redis configuration caused the incident."

Evidence:
- Redis metrics
- application logs
- configuration snapshot
- timeline
- reproduction/test
```

A document may contain a claim without sufficient supporting evidence.

Therefore the system must not treat:

```text
"The root cause was X"
```

as equivalent to:

```text
"X is demonstrated by evidence."
```

## 5. Evidence provenance

Every piece of extracted evidence should be traceable to its source.

### PDF

```text
source = PDF
document = PM-123.pdf
page = 8
section = Root Cause
element = Figure 2
```

### Jira

```text
source = Jira
issue = CHG-1234
location = comment #18
timestamp = ...
author = ...
```

### Confluence

```text
source = Confluence
page = ...
section = ...
```

Do not replace provenance with a generic chunk ID.

The system must be able to answer:

> "Where exactly did this evidence come from?"

## 6. Jira as a first-class source

Investigate how Jira should be integrated.

Do NOT assume:

```text
Jira → PDF
```

is appropriate.

Do NOT make Markdown the canonical representation either.

Instead investigate:

```text
Jira API
   ↓
Jira source representation
   ↓
Evidence extraction
   ↓
Canonical evidence model
```

A Jira ticket may contain:

- Description
- Comments
- Status
- History
- Fields
- Attachments
- Linked issues
- Approvals
- Resolution
- Dates
- Users

Determine which should become evidence and how provenance is retained.

## 7. Markdown as optional representation

Markdown can be useful as an intermediate representation for LLM context, for example:

```markdown
# CHG-1234

## Summary
...

## Implementation
...

## Comments

### 2026-07-29
...

## Linked Issues
...
```

But do not make Markdown the source of truth.

Investigate whether:

```text
Canonical structured representation
              ↓
       Context rendering
        ├── Markdown
        ├── JSON
        └── LLM-specific format
```

is appropriate.

## 8. Images and visual evidence

The system must support evidence contained in:

- Screenshots
- Graphs
- Monitoring dashboards
- Architecture diagrams
- Tables embedded as images
- Scanned documents

The original visual asset must remain associated with its source location.

For example:

```text
Evidence
 ├── type = visual
 ├── interpretation = ...
 ├── source = PM-123.pdf
 ├── page = 8
 └── asset = figure-2.png
```

Do not reduce visual evidence to OCR text alone.

## 9. Embeddings and vector search

Challenge the existing use of embeddings.

Ask:

- What exactly is currently embedded?
- Why is it embedded?
- Is embedding the correct abstraction?
- Should claims be embedded?
- Should evidence be embedded?
- Should sections be embedded?
- Should raw chunks still exist?
- Is vector search required for 40 documents?
- Would PostgreSQL + pgvector be sufficient?
- Can embeddings be treated as a retrieval index rather than the source of truth?

The conceptual model must not depend on a particular vector database.

## 10. Configurable audit criteria

The audit engine should not be hard-coded for postmortems.

Investigate:

```text
Audit Framework
    ↓
Audit Criteria
    ↓
Evidence Retrieval
    ↓
Assessment
    ↓
Finding
```

Possible frameworks:

```text
Postmortem Audit
Change Management Audit
Procedure Audit
Operational Control Audit
Custom External Audit
```

## 11. Presence vs sufficiency

Do not reduce audit analysis to:

```text
found = true
```

Investigate the distinction between:

### Presence

The document contains a statement addressing the criterion.

### Evidence

The document contains supporting information.

### Sufficiency

The evidence is sufficient to support the claim.

### Quality

The evidence has useful characteristics such as specificity, objectivity, completeness, and traceability.

### Gap

Important evidence is missing.

## 12. Cross-document analysis

The system should eventually support:

> What are the common failure patterns across these 20 postmortems?

> Which audit criteria are consistently poorly evidenced?

> Which procedures lack execution evidence?

> Are corrective actions consistently tracked?

Investigate whether the evidence model allows cross-document aggregation without reprocessing the original PDFs.

## 13. Reusability

A major architectural requirement is:

> **Do expensive extraction once, reuse the resulting evidence many times.**

Documents should be extracted once and then reused for:

- Audit #1
- Audit #2
- Audit #3
- Summary
- Cross-document analysis
- New auditor questions

## 14. Agent architecture

Challenge whether the current system is using an agent where deterministic processing would be better.

Prefer:

```text
Deterministic ingestion
        ↓
Document parsing
        ↓
Multimodal extraction
        ↓
Evidence normalization
        ↓
LLM reasoning
        ↓
Audit assessment
```

The agent should primarily reason/orchestrate over structured evidence.

# Important Constraints

Do not blindly implement the architecture described in this document.

This document is a **challenge**, not an implementation mandate.

Inspect the existing code first.

Prefer reuse where the existing design is sound.

Identify architectural debt before adding new abstractions.

Avoid premature infrastructure.

Do not introduce a graph database, vector database, event bus, or complex agent framework unless the actual requirements justify it.

The goal is a robust, explainable, provenance-preserving audit system — not maximum architectural complexity.

# Success Criteria

The resulting architecture should make the following possible:

```text
"Does this postmortem contain sufficient evidence
to support its root cause?"
```

```text
"Show me the exact evidence supporting this conclusion."
```

```text
"Where does this evidence come from?"
```

```text
"Is this evidence from a PDF, Jira, or another source?"
```

```text
"Find all evidence relevant to this audit criterion."
```

```text
"Which documents have evidence gaps?"
```

```text
"What common evidence gaps exist across 20 postmortems?"
```

```text
"Give me a summary, but cite the underlying evidence."
```

The system should be able to answer these questions without losing the connection to the original source material.
